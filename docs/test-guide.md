# Test guide

## 0. Agents verify on the real app before reporting (mandatory)
Every work package ends with the steps below, run by the agent on this PC. Windows needs no emulator.

1. **Build what you changed.**
   - UI and shell: `cargo tauri dev` (debug) or `cargo tauri build --target x86_64-pc-windows-gnu --features e2e --no-bundle`.
   - Core: only when the WP touches Kotlin, via `bash D:/Coding_Project/MinMusic-notes/tools/mm-build.sh D:/Coding_Project/MinMusic_4_Windows/core/MinMusic :desktopCore:sidecarImage`. This takes the global lock and 15–30 min, so batch your Kotlin changes into one build.
2. **Run** `powershell -ExecutionPolicy Bypass -File scripts/e2e.ps1 -Suite <wp-suite>`. It:
   - creates `.testdata\<run-id>` and sets `MINMUSIC_DATA_ROOT` to it. **Never use the owner's real `%LOCALAPPDATA%\MinMusic`.**
   - sets `MINMUSIC_DEVTOOLS_PORT` to a free port and `MINMUSIC_TEST_PIDFILE`
   - launches the built app with the real sidecar
   - waits for `core_status=ready`
   - runs `npx playwright test --project=app tests/e2e/<suite>` attached over CDP
   - saves screenshots, `Page.captureScreenshot` via CDP only (GDI and PrintWindow are unreliable here), to `.testdata\<run-id>\shots\`
   - runs the process checks (§3) in PowerShell
   - stops **only the PIDs from its own pidfile**, never by image name
3. **For UI work, look at the screenshots yourself** against the MK frame and fix any mismatch.
4. **If the WP can affect performance, run** `scripts/perf-trace.ps1 -Scenario <P#>`. These are all UI, shell, list and animation WPs.
5. **The report includes:** commands run, pass/fail counts, the screenshot paths, perf numbers if run, and anything not verified, with the reason.

Rules:
- DevTools/CDP is enabled only in debug or `e2e` builds through `MINMUSIC_DEVTOOLS_PORT`. Release builds must not be able to open it (test R-SEC-1).
- Agents must not kill processes they did not start. `Get-Process MinMusic` may include the owner's own instance.
- Keep the RAM use low: one app instance per agent at a time, and close it at the end of the run, even on failure (a `try/finally` in the scripts).

## 2. Contract tests (protocol)
- **Source of truth:** the types in `protocol/src/*.ts`. `npm run schema` generates `protocol/schema/*.json` (ts-json-schema-generator), one schema per method result and per event.
- **`tests/contract/` (Vitest, Node)** starts the **real prebuilt sidecar** from `sidecar/dist` with `MINMUSIC_DATA_ROOT=.testdata/contract`, a seeded DB fixture (`tests/fixtures/seed.db`, 5,000 songs, 40 albums, 10 user albums, generated by `tools/seed-db.mjs` through the core's own `userAlbum.*`/`import.files` API, not raw SQL) and `--fixture-home`. No Gradle is needed.
- For every method in api.md: call it, validate `r` against its schema, and assert one representative semantic (e.g. `library.window offset=4900 limit=200` → `items.length==100`, `total==5000`).
- **Subscriptions:** the first event is `*.snapshot`, `seq` increases, and a re-subscribe after a forced socket close gets a new snapshot.
- **Errors:** an unknown method → `bad_request`; a bad token → close 4401; a wrong Origin → rejected; `settings.get` of a secret key → `{set}` only.
- **Mock parity:** the same suite runs against `mock-core` (`--target mock`). The mock must pass 100 %, because UI tests rely on it.
- **Live-network tests** (`--live`, manual or nightly by hand only): `home.get` without fixture, `search.run "sơn tùng"`, play one YouTube track for 10 s, a Zing chart.

## 3. Process lifecycle tests (PowerShell, `scripts/e2e.ps1 -Suite process`)
They all use the test data root. "No orphan" means `Get-Process -Id <corePid>` fails, where `corePid` comes from the pidfile.

| ID | Steps | Pass |
|---|---|---|
| T-P1 | Start the app, wait ready. `taskkill /F /PID <shellPid>` | core PID gone within **2 s** |
| T-P2 | Start, play a fixture track, seek to 42 s, queue 5 items. Tray "Thoát" (via `invoke('app_quit')` over CDP) | both PIDs gone ≤ 4 s. Restart: `queue.window` total 5, current index and position 42 ± 1 s restored, paused |
| T-P3 | Start. `Stop-Process -Id <corePid> -Force` | `core_status` goes `restarting` then `ready` ≤ 5 s. The UI shows the restart banner, then hides it. `player` resubscribed (snapshot received). Exactly one core PID afterwards |
| T-P4 | Start. Launch the same exe again with the same `MINMUSIC_DATA_ROOT` | the second process exits ≤ 2 s, the main window is focused, and `Get-CimInstance Win32_Process` shows exactly one `minmusic-core.exe` whose ParentProcessId is our shell |
| T-P5 | Start, then kill the shell with `taskkill /F` *and* suspend job assignment (test build flag `MINMUSIC_TEST_NO_JOB=1`) | core exits ≤ 3 s via stdin EOF / parent poll (the safety net works alone) |
| T-P6 | Write a fake stale `core.pid` pointing at a running test-started `minmusic-core.exe --cds-warmup-idle` from our dist; start the app | the stale process is killed before spawn, the app is ready, one core |
| T-P7 | Kill the core 4 times within 120 s | after the third crash the fatal screen shows; no restart loop; no orphan after quit |
| T-P8 | × with default settings | window hidden, both PIDs alive, `player.state.playing` stays true for 10 s |
| T-P9 | Set `minimizeToTrayOnClose=false`, × | normal quit, both gone ≤ 4 s, queue restored next start |
| T-P10 | Session end: send `WM_QUERYENDSESSION` then `WM_ENDSESSION(TRUE)` to the main hwnd (test helper `tools/sendmsg.ps1` with `user32!SendMessageTimeout`) | the handler returns within 3.5 s, the queue is saved (verified on next start), the core exits |
| T-P11 | A v1-style held lock: open a `FileStream` lock on the test root's `metrolist.lock` from PowerShell, then start | the app shows the "MinMusic 1.x đang chạy" message, no core left running |
| T-P12 | The installer stops processes: run the NSIS setup `/S` over a running test install (M5) | both processes stopped before files are replaced; the install succeeds |

## 5. Performance measurement (scripts to write in M0-E)
**`scripts/perf-trace.ps1 -Scenario P1|P2|…|all -Size 4k|1920 -Runs 5`**:
1. Builds (or reuses) the release + `e2e` binary. Starts it with a test data root, `MINMUSIC_DEVTOOLS_PORT`, and the fixture Home and seed DB.
2. Waits 10 s for warm-up (JIT, image cache), then runs the scenario driver `tools/perf/run.mjs`:
   - Playwright `connectOverCDP`.
   - CDP `Tracing.start` with categories `benchmark,graphics.pipeline,cc,viz,gpu,input,devtools.timeline,disabled-by-default-devtools.timeline.frame,blink.user_timing`, `transferMode: ReturnAsStream`.
   - **Input via OS events, not DOM events,** so the compositor path is exercised. Wheel notches go through `tools/perf/sendinput.exe` (a tiny Rust bin in `tools/perf/`, `SendInput` `MOUSEEVENTF_WHEEL` ±120 with 200 ms spacing), at the list centre.
   - Clicks use CDP `Input.dispatchMouseEvent` (acceptable for P3/P4 because the latency is measured from the event timestamp).
3. In parallel it runs **PresentMon 2.x** (downloaded once to `tools/perf/bin/`, version pinned, SHA-256 checked) capturing process `msedgewebview2.exe` to CSV for the scenario window.
4. Parses with `tools/perf/analyze.mjs`:
   - **Frames:** trace events named `PipelineReporter`, top-level only, reading `args.chrome_frame_reporter.state` (fallback `args.data.state`).
     - dropped % = (DROPPED + PRESENTED_PARTIAL) / (all − NO_UPDATE_DESIRED)
   - **Long tasks:** `RunTask` on `CrRendererMain` > 50 ms.
   - **Input latency:** `EventLatency` duration p95.
   - **PresentMon:** count of `MsBetweenDisplayChange > 25` within the scenario window.
     - Map columns by header name. PresentMon versions rename columns; the script asserts the needed columns exist.
5. **Calibration (must pass before any result is trusted):** scenario `CAL` injects a 120 ms busy loop every 1 s during a scroll. The analyzer must report ≥ 1 long task per second and dropped frames > 0. With no injection, on the mock idle page, it must report 0.
6. Output goes to `docs/perf/<date>-<scenario>-<size>.json` plus a Markdown row appended to `docs/perf/results.md` (the worst of N runs, with the median shown too).

**Startup (S1, S2):** `tools/perf/startup.ps1` launches 10 times (warm).
- S1 is `shell spawn → performance.mark('mm-first-home-paint')` (exposed by the e2e build at `window.__mmMarks`).
- S2 is from the shell log `READY` timestamp.
- Cold starts are measured by hand once after a reboot.

**Memory and CPU (R1, R2, C1):** `tools/perf/resources.ps1` samples `Get-Process -Id` for the shell, its WebView2 children (found by ParentProcessId walk) and the core every 1 s, recording `PrivateMemorySize64` and the CPU delta.

**Size (I1):** the release workflow prints the setup and installed sizes. Local check: `scripts/size.ps1`.

**Resolution setup:**
- 3840×2400 is the native panel at the owner's scale (record the scale in the report).
- For 1920×1200, set the window to 1920×1200 physical px via `test_set_window_size` at a 100 % per-monitor scale override (e2e build only: `--force-device-scale-factor=1` in the additional browser args), so the GPU load matches a 1920×1200 surface.

## 8. Security checks
- **R-SEC-1:** the release build ignores `MINMUSIC_DEVTOOLS_PORT`; `curl http://127.0.0.1:<port>/json` fails.
- **R-SEC-2:** the core rejects a WS client without the token and with a foreign Origin (contract suite).
- **R-SEC-3:**
  - `rg -a "<test NCT password>" .testdata/` finds nothing after an NCT login test.
  - The same check for the Last.fm password.
  - `secrets.properties` is not plaintext (starts with the DPAPI blob header after base64 decode).
- **R-SEC-4:** the CSP blocks a test fetch to `https://example.com` from the UI console.
- **R-SEC-5:** `scripts/check_no_ads.sh` passes. `rg -i "analytics|telemetry|sentry\.io|google-analytics|gtag"` finds nothing in `ui/src` or `src-tauri/src`.
